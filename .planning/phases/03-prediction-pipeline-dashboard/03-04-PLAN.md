  <action>
    Create `scripts/replay_race.py`, a dev-only CLI (argparse, `ArgumentDefaultsHelpFormatter`). Flags: `--source-session-key` (int, required — the completed historical race to replay), `--target-session-key` (int, optional; default = source, replay in place), `--interval` (float seconds per lap, default `5.0` per D-03 fast default; a value like `60`–`100` gives realistic pacing), `--db` (optional path, default the project DB via get_engine()). Behavior: read the DISTINCT ordered `lap_number` values present in `raw_laps` for the source session; loop lap by lap, and for each lap SELECT that lap's rows from `raw_laps`/`raw_positions` (plus the current `raw_stints`/`raw_pit_stops` snapshot up to that lap) via `text()` + bound `:param`, re-INSERT them into the SAME raw_* tables (for the target session_key) using `bulk_insert_rows`, then `time.sleep(interval)` before the next lap. This mimics `poll_once`'s incremental arrival of new laps so the running `pipeline.py` picks them up and fires inference (Pattern 1). Use a plain `time.sleep` loop (not APScheduler — this is a one-shot script, per PATTERNS). Guard target inserts so re-running is safe (skip laps already present for the target, mirroring the poller dedupe gate). Reuse `get_engine()`; never build a second engine factory. No f-string SQL.

    Add `tests/test_replay_race.py`: seed a tmp_engine with a source race's raw_laps across laps 1..N; call the replay's per-lap insert function (factored out for testability, e.g. `replay_lap(engine, source_sk, target_sk, lap_number)`) with `interval` bypassed; assert rows land in the target session incrementally and re-running a lap does not duplicate.
